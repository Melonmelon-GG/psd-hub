# 色彩模式与颜色通道支持

> ⚠️ **本文描述的能力在 v2.0 路线中已不接入。**
>
> 项目在 v2.0 把技术路线从「上传 PSD + 浏览器解析预览」改为「**上传 PNG + 网盘分享链接**」，
> 因此浏览器端 PSD 解析、图层预览与自研多色彩模式解码器**都不再被界面与路由使用**。
>
> 相关代码**按用户要求完整保留在仓库中**（`frontend/src/psd/**`、`frontend/src/components/PsdViewer.tsx` 等），
> 仍然可编译、其测试仍然全绿，只是没有任何生产代码引用它。本文因此保留为**技术存档**：
> 若将来恢复在线预览，按本文的结论接回即可，无需重新调研。
>
> 当前路线的契约见 [`API.md`](./API.md)。

本文记录 PSD 展示台对非 RGB 工程的完整支持情况、实现依据，以及调研过程中发现的**两个真实格式陷阱**。

> 结论先行：**CMYK 工程可以在浏览器里正确预览并逐层切换显隐**，换算公式与 Pillow 的解码结果逐像素一致。

---

## 1 · 为什么需要自研解码器

前端原本依赖 `ag-psd` 做浏览器端 PSD 解析。实测发现它的**实际**能力边界比预期窄得多：

```js
// ag-psd/dist/psdReader.js
exports.supportedColorModes = [ColorMode.Bitmap, ColorMode.Grayscale, ColorMode.RGB, ColorMode.Indexed];
```

不在这个列表里的色彩模式，`readImageData()` 会直接抛 `Color mode not supported: <mode>`。也就是说：

| 色彩模式 | ag-psd 行为 |
| --- | --- |
| Bitmap / Grayscale / RGB / Indexed | 可以读 |
| **CMYK** | 抛错 |
| **Lab** | 抛错 |
| **Multichannel** | 抛错 |
| **Duotone** | 抛错 |

另外还发现 `ag-psd` 的 **16 位 RLE 路径有缺陷**：它按「1 字节/样本」处理行数据，而 16 位是 2 字节/样本，导致每行写满 `width` 字节后就停止，样本逐步错位。用 16 位 RGB 素材实测，与参考图 MAE = 81.32、最大差 255（而正确结果应为 0）。

因此引入了**双引擎**架构：

```
PSD 字节
   │
   ├─ 读 26 字节文件头 → colorMode / bitsPerChannel
   │
   ├─ 8 位 且 模式 ∈ {Grayscale, Indexed, RGB} ──► ag-psd 主引擎
   │                                               （保留图层样式、调整层等完整信息）
   │
   └─ 其余（CMYK / Lab / Multichannel / Duotone / 所有 16 位）──► 内置兜底解码器
                                                                 （自带图层树解析）
```

内置解码器在 `frontend/src/psd/decode/`，零依赖、不碰 DOM，因此既能在浏览器跑，也能在 Node 里做逐像素回归测试。

## 2 · 两个真实的格式陷阱

这两个坑都是靠**第三方实现交叉验证**才发现的 —— 只用自研代码验证自研生成的素材，等于自己证明自己。

### 陷阱一：CMYK 存的是「反相墨量」

PSD 里 CMYK 通道存的**不是**墨量，而是反相值：

```
255 = 没有该色油墨
  0 = 该色满版
```

换算到屏幕 RGB 的公式是**乘性**的：

```js
R = Math.round(S_C * S_K / 255)
G = Math.round(S_M * S_K / 255)
B = Math.round(S_Y * S_K / 255)
// S_* 是文件里的原始字节
```

等价的墨量写法是 `R = 255 × (1 − C_ink) × (1 − K_ink)`。

**怎么确认的**：把同一份 CMYK 素材交给 Pillow（完全独立的实现）解码，与我们的参考图逐像素比对，MAE = 0.00。反过来，把 `load()` 返回的值与「反相 + 乘性」两步推算出的值对齐，也完全吻合；而「加性公式」（`255 − C − K`）在同一批采样点上明显对不上。

> 如果按墨量直接解释（少做一次反相），画面会整体反色 —— 这是最典型的踩坑表现。

### 陷阱二：Indexed 调色板是「平面」存放

索引色模式的 color mode data 段固定 768 字节。它**不是** RGB 交错（`R0 G0 B0 R1 G1 B1 …`），而是**平面**排列：

```
字节 [0..255]     → 全部 256 个 R
字节 [256..511]   → 全部 256 个 G
字节 [512..767]   → 全部 256 个 B
```

即 `palette[i] = { r: data[i], g: data[256+i], b: data[512+i] }`。

**怎么确认的**：`ag-psd` 与 `Pillow` 两个互不相干的实现，对我们那份**交错**写法的文件读出了**完全相同**的错误调色板（`palette[0] = (0,102,102)`）。既然两者一致，说明它们读的是同一个规范。按平面解读我们文件里的字节，逐项复现了它们的读数 —— 于是确定是**我们写错了**，而不是两个库都错了。修正后，两库与参考图的 MAE 双双从 61.93 降到 **0.00**。

### 附带修正：Lab 要用 D50，不是 D65

Photoshop 的 Lab 模式以 ICC PCS 的照明体 **D50** 为参考白。最初按常见的 D65 实现，Lab 工程解出来整体偏色（与 Pillow 的 Lab 解码 MAE≈66）。改用 D50（Lindbloom 的「sRGB with D50 white point」矩阵）后，往返验证对原始画面 MAE≈0.43 —— 忠实还原。

## 3 · 支持矩阵与精度分级

产品上把精度分成三档，并在界面上**明确标注**，避免用户误以为预览就是 Photoshop 的最终效果：

| 分级 | 含义 | 覆盖 |
| --- | --- | --- |
| **精确** | 与 Photoshop 解码逐像素一致 | RGB、Grayscale、Indexed（8 位）、Bitmap |
| **色彩换算** | 色彩空间换算有固有误差，视觉一致 | **CMYK**、**Lab**、16 位 |
| **近似预览** | 语义上就只能近似 | **Duotone**（按灰度）、**Multichannel**（按前 3 通道） |

分级定义在 `frontend/src/psd/colorModes.ts`，是前端关于色彩模式的唯一真相来源，负责回答三件事：模式名称与基色通道数、保真度分级、该走哪条引擎。

### 各模式的通道构成

| 模式 | 基色通道 | 说明 |
| --- | --- | --- |
| Bitmap / Grayscale / Indexed / Duotone | 1 | |
| RGB / Lab | 3 | |
| CMYK | 4 | C、M、Y、K |
| Multichannel | **不固定** | 除基色外还可有任意多个专色通道，因此**无法**据此判断是否含 alpha（后端的 `hasAlpha` 对此返回 `null`） |

文件头的「通道数」= 基色通道数 + 可选 1 个 alpha。后端的 `hasAlpha` 就是按这个规则推导的。

## 4 · 位深与压缩

| 维度 | 支持情况 |
| --- | --- |
| 位深 8 位 | 完整支持 |
| 位深 16 位 | 支持，取高字节降到 8 位（`v × 257 >> 8 === v`，往返无损） |
| 位深 32 位浮点 | 尽力而为（读大端 IEEE-754，clamp 到 0..1） |
| 位深 1 位（Bitmap） | 支持（按位展开，行内高位在前） |
| 压缩 raw(0) | 支持 |
| 压缩 RLE(1) | 支持（PackBits） |

**RLE 的行长度表位置容易写错**，两种场景不一样：

- **图层通道**：每个通道的数据块自成一体 —— `2 字节压缩标志 + height 个行长度 + 各行的 PackBits 数据`
- **合成图像**：整段开头一个压缩标志，然后是**全部通道 × 全部行**的长度表，顺序为「通道优先」（先 channel0 的全部行，再 channel1 的…），最后才是各通道的行数据

## 5 · 验证方式

| 工具 | 作用 |
| --- | --- |
| `npm --prefix frontend test` | 解码器对全部素材做逐像素回归（与裸 RGBA 参考数据比对） |
| `npm run verify:fixtures` | 素材结构校验 + 用 `ag-psd` 交叉比对（零依赖） |
| `python tools/pillow-crosscheck.py` | 用 `Pillow` 独立交叉验证（需 `pip install Pillow`） |
| `npm run smoke` | 端到端：上传各色彩模式的工程并核验元数据与下载字节 |

素材由 `tools/make-sample-psd.mjs` **手写字节流**生成，覆盖 7 种色彩模式 × 8/16 位 × raw/RLE，
并为每份 PSD 导出：

- `<名>.png` —— 画面（人眼可看，也供交叉验证）
- `<名>.rgba` —— 裸 RGBA 字节，测试零依赖比对

> 生成器本身也是「对格式理解是否正确」的独立参照物：它与解码器是两套独立代码，
> 一边写、一边读，能对上的前提是双方对规范的理解都正确。

## 6 · 已知限制

1. **Duotone 未应用双色调曲线**：需要解析文件里的双色调选项块，当前按灰度预览，界面标注为「近似预览」。
2. **Multichannel 按前 3 通道近似**：多通道文档常含专色通道，没有通用的屏幕显示规则。
3. **无 ICC 特性文件的色彩管理**：CMYK/Lab 使用标准换算公式。若 PSD 内嵌了自定义 ICC 特性文件，与 Photoshop 的色彩管理结果会有可感知差异。要做完整色彩管理需引入 lcms（wasm 版）并读取图像资源段里的 ICC 块 —— 属于后续可扩展项。
4. **32 位浮点仅尽力而为**：不作为主要支持目标。
5. **解析在主线程**：超大 PSD 会有短暂卡顿，已有 >150MB 二次确认与加载骨架屏。
